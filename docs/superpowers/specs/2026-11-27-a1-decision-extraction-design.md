# A1 Hero Decision Extraction Design

## Intent and boundary

Produce source-backed, deterministic context for each meaningful Hero betting decision in an imported NLHE hand. This is input for a later Strategy Engine, not an assessment of play. A1 stays in `src/domain`, has no React, network, AI, recommendation, grade, EV, or persistence dependency, and does not alter the Nocturne UI. Work starts from the clean `feature/a1-decision-extraction` branch based on merged `main`; no commit, push, merge, or deploy is part of A1 delivery.

The source is the canonical `ImportedHand` produced by the existing GG parser. A1 does not parse `source.rawText`, reinterpret rendered replay strings, or introduce another hand-history format. Its output is stable for a given hand and event order, independent of final result and awards.

## Approaches considered

1. **One pass over `ImportedHand.events` with `HandLedger` (chosen).** The ledger owns chip accounting; a small A1 tracker owns betting rules and preflop sequence. This gives each Hero event its pre-action state without replaying earlier events repeatedly.
2. Rebuild replay at every Hero action. This exposes convenient snapshots but repeats prior work, couples extraction to a presentation-oriented projection, and still needs a separate minimum-raise and reopening tracker.

The user selected approach 1. The replay model remains a test oracle for representative decisions.

## Canonical event source and decision identity

Read `ImportedHand.events` in source order. A decision is a Hero `FOLD`, `CHECK`, `CALL`, `BET`, or `RAISE` on `PREFLOP`, `FLOP`, `TURN`, or `RIVER` with chips available to act. Forced posts, antes, board changes, returns, awards, reveals, showdown, and opponent actions are not decisions. The known zero-stack forced-post fold anomaly is retained in the source and reported as a diagnostic, not counted as a meaningful Hero choice.

Each decision records `handId`, the source `eventId` and line number, and a contiguous zero-based `decisionIndex` assigned in event order. Multiple Hero actions on one street receive distinct indices. The current street comes from the event; board cards come from that street's cumulative `ImportedHand.streets` entry, so future board cards never appear. Position and hole cards come from the imported domain hand, not from UI labels. `playersDealt` is occupied seats; `playersInHand` counts non-folded players including all-in players.

**Recoverable action anomalies and fatal hand invalidation are separate outcomes.** A known, ledger-supported anomaly such as `ZERO_STACK_FOLD` is a recoverable non-decision: skip that action, attach its source event/line and warning code to a diagnostic, continue the pass, and retain every other valid Hero decision. A fatal structural or accounting failure (invalid canonical shape/order/actor, impossible ledger movement, or incomplete accounting) excludes the _entire hand_: return no decisions, including none accumulated before the failure, and report the fatal reason. Do not broaden the recoverable list merely to keep a hand eligible. Anomaly diagnostics never substitute for ledger validation.

## Ownership during the pass

**`HandLedger` owns:** starting and changing stacks, total pot, each player's gross contribution and returns, current-street live commitment and bet, the amount faced and stack-capped amount to call, and validation of event chip movements. The extractor reads its snapshot and these ledger-derived wager values _before_ applying each event. Narrow read accessors for current live bet, amount faced, and call amount reuse the wager calculation already inside `apply`. A `beginStreet(street)` operation exposes the ledger's existing street reset before the first event on a new street. `apply(event)` continues to perform that reset idempotently for existing callers. This avoids reading previous-street commitments on an opening action. A1 must not create another stack, pot, or current-bet accumulator.

**A1 betting tracker owns:** last full raise increment, short all-in raises, each player's last acted wager and raise-reopening threshold, folded players, preflop voluntary actions and raise count. It resets street-specific rights at each street boundary. It uses ledger wagers, commitments, and stacks when deciding whether a raise is allowed or another player can contest it. It does not duplicate ledger chip movement or current-bet accounting. If source action sequence makes a legal-action conclusion ambiguous, it emits `legalActions: null` with a reason; it does not silently claim a raise is legal.

**Replay cross-check:** tests project curated representative canonical hands with `toReplayHand`, locate each source event with `findActionCursor`, and compare `buildReplayState` immediately before that action against A1. Acceptance requires _exact agreement_ for pre-action pot, Hero pre-action stack, visible board, and the non-folded player-ID set at each selected decision, including blind option, repeated Hero action, later street, all-in, and multiway cases. The target is **zero unexplained discrepancies**. Known documented source anomalies are reported separately with event/line evidence, never normalized away to make the comparison pass. Replay is not called by the production extractor, and replay's UI-oriented state is not the A1 contract.

## A1 contract

Create a separately named `HeroDecisionContext` and a pure `extractHeroDecisions(hand: ImportedHand): DecisionExtractionResult` API. `DecisionExtractionResult` carries decisions plus source-backed diagnostics; an invalid canonical hand, including one whose later event fails ledger validation, yields an explicit excluded result with no partial decisions. Runtime input validation uses the existing imported-hand schema and checks ordered/unique events and actor references. A1 does not use `inspectMetricHand` wholesale: that metric-specific boundary excludes an entire hand for `ZERO_STACK_FOLD`, whereas A1 retains other valid decisions and skips that anomalous action. The primary extraction loop applies each event once; structural validation is not a second interpretation of poker action.

Each context contains identity/evidence, street, Hero position/cards, visible board, player counts and compact non-folded player contexts, pre-action pot/stack/contributions, wager/call values, legal actions, actual action and size, effective stack, pot type, preflop sequence, and deterministic source confidence/reasons. Use existing `Position`, `Card`, and street types. The current `ImportedHand` schema requires Hero hole cards, so missing Hero cards now make the hand invalid; a nullable A1 card field protects future canonical versions that may represent genuinely unknown cards. Chip fields are safe integers. BB and pot ratios are numbers only when their denominators are known and positive; otherwise they are `null` with a reason where interpretation matters. `null` never means zero.

The existing `DecisionContext` in `src/domain/schemas.ts` is a Phase 0 mock analysis contract with `categories`, `triage`, and a required effective-stack value. Reusing it would force uncertain source facts into a non-null number and mix deterministic extraction with grading and review concerns. A1 leaves that contract and its current consumers unchanged; a later integration can explicitly map A1 facts into analysis contracts.

## Pre-action amounts and legal betting actions

Ledger-derived `currentBetChips` is the highest live street wager Hero must match, with the nominal BB as the preflop floor. Ledger-derived `facingAmountChips` is the uncapped difference between that wager and Hero's live commitment. Ledger-derived `amountToCallChips` is the chips Hero can actually add to call, capped by the pre-action Hero stack. The distinction exposes a short all-in call. `potBeforeActionChips` includes all prior contributions, including antes and blinds, less valid prior returns. It never includes Hero's current action or later awards.

If nothing is owed, check is available. Bet is available when there is no live wager, Hero has chips, and another player can contest; the BB preflop option is check or raise because a nominal wager exists. If a wager is owed, fold and call are available; check is not. Raise is available only when Hero has chips beyond a call, another player can contest, and betting has reopened. A full raise must meet the last full increment; a smaller raise is allowed only when it is Hero's all-in maximum and raising rights otherwise exist. Source-backed short all-ins do not automatically reopen action for players who already acted. An unresolvable reopening or unsupported raise sequence makes legal actions unknown with an audit reason. An `ALL_IN` flag describes a call, bet, or raise; it is not a separate replacement action kind.

`actualAction` preserves the canonical action kind and `isAllIn`. `amountAddedChips` is the event's incremental chip movement; `raiseToChips` is present only for raises. For fold/check, added chips are zero. BB sizing divides added chips by the hand's actual big blind. Pot fraction uses added chips over the pre-action pot only when that pot is positive and the ratio has a meaningful betting interpretation; otherwise it is null. The extractor records actual source events even where legal availability is unknown, with a diagnostic rather than retroactively changing the source.

## Effective stack and player context

Each non-folded player context gives source seat/position, pre-action stack, street commitment, and active/all-in state. For exactly one contesting opponent, `effectiveStackBeforeChips` means **additional Hero chips that can be contested against that opponent from this point**: `min(heroStackBefore, opponentStackBefore + max(0, opponentCommitment - heroCommitment))`. This accounts for a wager already committed by an opponent who is now all-in. It is not a starting-stack statistic. With multiple contesting opponents, the scalar is null with `multiway_effective_stack_ambiguous`; the per-player contexts preserve the information needed by later analysis. Normalize a known effective stack by the actual BB. No opponent tendencies or inferred ranges are included.

## Structural context and unknowns

`potType` is based on preflop voluntary raises observed so far: unopened before any voluntary call or raise; limped/checked-blind pot with calls but no raise; single-raised after one raise; 3-bet after two; 4-bet-plus after three or more. A postflop decision retains the completed preflop classification. `preflopSequence` is an ordered array of source-backed voluntary actions with actor ID, position, action, all-in flag, incremental amount, and raise-to where applicable. On a preflop decision it stops immediately before Hero's current action; on later streets it is complete. Forced posts are excluded from this sequence.

`sourceConfidence` is a deterministic `confirmed | partial | unknown` classification, never a probability or solver confidence. Diagnostics and field-level reasons identify source warnings, ambiguous effective stack, missing optional evidence, unsupported raise/reopening, and invalid hand input. Source-backed facts remain available when only a derived field is unknown. The known `SHORT_BLIND_POST` and `ZERO_STACK_FOLD` warnings retain their existing parser meanings; A1 does not rewrite those fixtures or their accounting.

## Verification and delivery

Use focused TDD, beginning with preflop open/facing-open and extending to blinds, repeated Hero actions, each street, short all-ins/reopening, heads-up/multiway, returns, warnings, and invalid input. Cross-check representative pre-action snapshots with replay under the exact-agreement criteria above. Audit the immutable GG corpus without changing fixture bytes or SHA manifest. The corpus acceptance gate is: **zero unexpected extraction failures; zero unexplained A1/Replay discrepancies; a deterministic reason for every unknown critical field; unchanged immutable fixture bytes and SHA; decisions reported by street and actual action; and a curated representative sample of extracted `HeroDecisionContext` records prepared for manual poker review.** Report hands with zero decisions, exclusions, unknown reasons, recoverable anomalies, and any known documented discrepancies separately. Add a concise technical contract at `docs/specs/hero-decision-extraction.md` with the implemented semantics and known ambiguities. Run focused tests and the corpus audit during implementation; provide numbered broad verification commands for the user. Stop at **A1 — READY FOR REVIEW** without a commit or UI integration. Phase 2 remains incomplete after A1.
